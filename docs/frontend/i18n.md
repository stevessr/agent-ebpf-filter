# WebUI language switching and per-page acceptance

The browser workbench supports **简体中文 (zh-CN)** and **English (en-US)**.
The selector is in the top toolbar next to workspace controls. Selecting a
language takes effect without refreshing the page and persists in localStorage
(`agent.webui.locale.v1`). The default remains simplified Chinese for
compatibility with existing user installations.

## Architecture

- `src/i18n/messages.ts`: shared UI translation catalog.
- `src/i18n/index.ts`: reactive locale, persistence, HTML `lang` and title,
  plus a compatibility bridge for existing components.
- `src/App.vue`: language selector and dynamic Ant Design Vue locale.
- `src/components/workbench/`: explicitly translated shell, tab and breadcrumb
  labels. Theme switching is independent of locale state.

Use `translateUI("中文词条")` from components for new UI text. For existing
Vue components, the compatibility layer currently updates **only exact,
cataloged UI labels** and selected accessibility attributes. It deliberately
does not alter program source code, terminals, captured logs, table records,
or arbitrary user data. This is a migration bridge, **not** machine translation.
For complete localization of a domain-specific page, add all of its UI strings
to the catalog and move text into reactive bindings; avoid relying on DOM
rewrites for new components.

## Browser acceptance via GitHub Actions

`.github/workflows/webui-i18n-acceptance.yml` runs after pushes and pull
requests affecting the frontend, and can also be triggered manually. It
uses four independent shards and validates 25 routes and subpages.

For each route, Chromium checks:
1. The page loads and shows a valid workspace container.
2. The English locale changes the navigation and HTML language.
3. Dark-mode appearance is applied live, then light mode is restored.
4. Chinese labels reappear when switching back without navigation.
5. Locale selection survives full reloads in both languages.
6. The viewport is not wider than the browser, and there are no uncaught
   browser exceptions.

Every route produces English/light, English/dark and Chinese/light screenshots,
a JSON verdict and an aggregated shard summary. GitHub displays per-route
pass/fail tables in the workflow summary; artifacts are retained for 14 days.
The test is intentionally a **frontend/offline render acceptance**: it does
not prove that a real Linux eBPF backend is functioning, nor that every
unmapped legacy string has been translated.

To reproduce with a local backend-independent Vite server and Playwright:

```bash
cd frontend
bun install --frozen-lockfile
bun run dev -- --host 127.0.0.1 --port 5173
# In another terminal with playwright installed and Chromium available:
WEBUI_SHARD=0 WEBUI_SHARD_COUNT=4 node scripts/test-i18n-pages.mjs
```

The frontend unit check is `bun test tests/i18n.test.ts`, and
`.github/workflows/frontend-build.yml` runs it alongside TypeScript/Vite.
