Agent eBPF Filter 商业企划书

0. 执行摘要

Agent eBPF Filter 是面向 AI Agent 与开发者 CLI
的运行时安全与可观测平台。随着 Codex、Claude Code、Gemini
CLI、Copilot、MCP 工具和企业内部自动化 Agent
进入研发流程，企业与高校正在面对新的安全问题：Agent
不只生成文本，还会启动
shell、安装依赖、读写文件、访问网络、操作浏览器和调用外部工具。传统提示词安全无法证明真实执行行为，传统
EDR 又缺少 Agent 任务语义。本项目以 eBPF 为事实采集和内核阻断底座，将
Agent 的语义声明、操作系统事实和策略控制统一起来，形成“黑匣子 +
刹车系统”。

商业化路径采取“开源核心 + 专业版 + 私有化 +
教育培训”的组合：开源基础观测能力积累开发者社区；专业版服务高校实验室、AI
coding
团队和安全研发团队；私有化版本进入企业内网与研发效能平台；教育版配套课程、实验和竞赛训练营。

  注：本企划书中的价格、收入和客户数量为校赛版测算，提交前应使用真实访谈、试点意向、合同报价或学校/企业反馈进行替换。

1. 项目愿景

让 AI Agent 在真实开发环境中“敢用、可控、可证据化”。

- 敢用：不是简单禁用 Agent，而是在可观测、可回放、可审计的边界内使用。
- 可控：对高风险文件、网络、命令执行路径提供确定性阻断和运行时门控。
- 可证据化：将每次 Agent
  执行链转化为时间戳、PID/TID、文件、网络、策略、告警和图谱证据。

2. 市场痛点

2.1 AI Agent 正在进入高权限工作流

AI
编码助手已经能够读取仓库、修改文件、执行测试、安装依赖、访问外部网络并提交
PR。运维、数据分析、客服和安全运营场景中的 Agent
也开始拥有工具调用、浏览器操作、数据库查询和脚本执行能力。外部调研显示，Agent
的主要风险不是“回答错”本身，而是工具权限、文件系统、网络访问、MCP/skills
配置和开发者本机凭据被串联成高权限执行链。GitGuardian 2026 报告将 AI
辅助提交、AI service key 和 MCP 配置列为 secrets sprawl
的增长因素；OWASP LLM06 则把过度功能、过度权限、过度自治列为 Agent
主要风险。

这意味着企业用户的真实问题不是“是否允许使用
Agent”，而是“如何在不牺牲研发效率的情况下，持续看见并约束 Agent
到底做了什么”。

2.2 现有方案缺口

  ----------------------------------------------------------------------------------------------------------
  方案                 能力                         缺口
  -------------------- ---------------------------- --------------------------------------------------------
  Prompt/内容安全      检查输入输出、阻止敏感文本   看不到真实进程、文件、网络行为。

  EDR/主机安全         监控系统行为、恶意软件检测   不理解 Agent run/task/tool_call
                                                    语义，难判断是否偏离用户意图。

2.3 高价值痛点

- 密钥外泄：Agent 读取 .ssh、.env、云凭证、浏览器 cookie、MCP 配置或 CI
  token 后，普通日志很难证明是否外传。
- 只读任务漂移：Agent 在“只读分析/PR review”任务中启动
  curl|bash、nc、ssh、python -c 等异常命令，用户直到事后才发现。
- 供应链执行链：npm install、pip install、Git hooks、MCP skills
  或依赖脚本借 Agent 权限访问本机资源。
- 多 Agent 协作冲突：多个 Agent 同时修改同一文件或同一任务链，缺少
  PID、task、tool_call 级别归因。
- 审计不可证明：企业想使用 Agent
  提效，但安全/合规团队缺少可验证、可回放、可提交给管理层的证据材料。

3. 产品与解决方案

3.1 产品定位

Agent eBPF Filter 是部署在 Linux 开发机、实验室服务器、企业研发节点或
Kubernetes 节点上的 Agent Runtime Security & Observability Plane。

一句话定位：把 Agent 的“承诺”与操作系统里的“事实”对齐起来。

3.2 产品模块

  -------------------------------------------------------------------------------------------------------
  模块                 功能                                      客户价值
  -------------------- ----------------------------------------- ----------------------------------------
  内核事实采集         eBPF 捕获                                 获得无法被普通应用日志替代的真实证据。
                       exec/open/connect/send/recv/fork/unlink   
                       等行为                                    

  Agent 语义接入       wrapper、CLI hooks、Python/Node 适配器    知道事件来自哪个 Agent、任务和工具调用。

  策略阻断             BPF LSM、cgroup、wrapper                  将审计提升为可执行控制。
                       ALLOW/BLOCK/ALERT/REWRITE                 

  执行图谱             Agent Run -> Tool Call -> Process ->      事故复盘、答辩演示、审计汇报更直观。
                       File/Network/Policy                       

  ML/LLM 风险评分      训练样本、benchmark、原因码、建议策略     持续优化误报/漏报，不让 LLM

3.3 典型使用流程

1.  管理员启动 Agent eBPF Filter 后端并加载 eBPF 程序。
2.  开发者通过 agent-wrapper 或 CLI hook 启动 Codex/Claude/Gemini
    等工具。
3.  Agent
    执行任务时，系统记录工具意图、进程树、文件访问、网络流和策略决策。
4.  如果出现敏感文件访问、异常网络外联、下载即执行、工作区逃逸等行为，系统告警或阻断。
5.  用户在 Execution Graph 中回放证据链，并一键生成 allow/block
    规则或训练样本。

4. 核心技术壁垒

4.1 eBPF 与 BPF LSM 工程壁垒

系统覆盖 syscall tracepoints、cgroup/connect、UDP sendmsg、BPF LSM、TLS
uprobe（默认关闭）等多类 hook，并处理 pin
maps/links、权限、自提升、内核兼容和缺失 tracepoint
容错。这类能力需要系统编程、内核安全和 Go
工程协同，不容易被只做前端或单纯大模型应用的团队快速复制。

4.2 Agent 语义与 OS 事实的统一事件模型

项目把 hook/wrapper 语义、eBPF 事实、策略决策、ML/LLM 风险评分统一到
EventEnvelope，并保留
agent_run_id、task_id、tool_call_id、trace_id、PID/TGID/PPID、cgroup_id
等字段。这使平台能解释“某个工具调用为什么触发某个系统行为”，而非只有零散日志。

4.3 执行图谱与数据闭环

图谱、录制、回放、导出、训练样本、基准测试连接成闭环。越多团队使用，越能积累高质量
Agent 行为样本与规则模板，形成产品数据资产。

4.4 安全边界设计

项目明确区分确定性阻断与智能分析：内核/cgroup/wrapper
策略负责同步阻断，ML/LLM
只提供解释、排序和建议，避免把不可解释模型直接放到高风险内核决策链路中。

4.5 代码实现形成的可防御壁垒

本项目的壁垒不只是“知道 Agent 安全有风险”，而是已经把风险落到 Linux
运行时证据与控制路径：

- lsm_enforcer.c 在 BPF LSM 决策点返回
  -EACCES，证明可以在行为完成前阻断。
- cgroup_sandbox.c 覆盖 TCP/UDP connect 与 UDP sendmsg，补上未连接 UDP
  sendto/sendmsg 的外联缺口。
- event_context.go 将 Agent 上下文继承到子进程，解决
  shell/python/node/git/npm/curl 行为归因。
- semantic_alerts.go 将密钥访问、异常外联、工作区逃逸、资源浪费循环、多
  Agent 文件竞争转化为可解释告警。
- ExecutionGraph
  将事件串成可演示、可复盘、可导出的图谱，直接服务安全审计和竞赛答辩。
